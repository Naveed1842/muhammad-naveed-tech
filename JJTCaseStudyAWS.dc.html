04 / CHALLENGES

What went wrong — and how it got fixed.

ECS tasks failing health checks after deploy
CHALLENGE 01 · DEPLOYMENT PHASE
RESOLVED
PROBLEM

New tasks cycled endlessly — started, killed at 60s, restarted. Zero successful deployments.

ROOT CAUSE

Spring Boot cold start exceeded the ALB health-check grace period; the check hit before the app was up.

SOLUTION

Raised health-check grace period, tuned JVM startup, pointed the check at a lightweight readiness endpoint.

RESULT & LESSON

Deploys green since. Lesson: health checks are a contract — design them with the app's startup profile, not defaults.

Task couldn't read database credentials
CHALLENGE 02 · DEPLOYMENT PHASE
RESOLVED
PROBLEM

Container booted locally but crashed in ECS with an access-denied error on startup.

ROOT CAUSE

The task execution role lacked permission to read the Secrets Manager entry — IAM roles for pulling images and running tasks are different.

SOLUTION

Scoped a least-privilege policy for exactly the two secrets the task needs and attached it to the execution role.

RESULT & LESSON

Clean boots, no wildcard permissions. Lesson: IAM errors are documentation errors — read which role does what.

07 / DEBUGGING STORIES

Real production debugging — with the terminal to prove it.

DEBUG 01
Container exits with code 137 in production only
3h to resolution
SYMPTOMS

Tasks dying silently ~40min after deploy. No stack trace, no error log — just gone.

INVESTIGATION

Exit code 137 = SIGKILL. Checked CloudWatch container insights → memory at 512MB ceiling. JVM saw the host's memory, not the container's.

FIX

Set container-aware JVM flags (MaxRAMPercentage=75), raised task memory to 1GB, added a CloudWatch alarm at 85%.

OUTCOME

Zero OOM kills since. Memory alarms now part of the standard task template.
